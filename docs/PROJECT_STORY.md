## 先解释几个绕不开的词

下面这些词在文中反复出现，第一次读的人先看这里。

| 词 | 意思 |
|---|---|
| Text-to-SQL | 给一句自然语言问题和一个数据库，让模型写出能回答这个问题的数据库查询语句（SQL）。 |
| BIRD | 一个公开的 Text-to-SQL 测试集，题目来自真实、比较脏的数据库。分 train（训练用，9428 题、69 个数据库）、dev（开发集）、mini-dev（从 dev 精选的 500 题）。 |
| 执行准确率（EX） | 判断模型写的 SQL 对不对，不看文字像不像，而是真的在数据库上跑一遍，比较查询结果和标准答案的结果。对记 1 分，错记 0 分。 |
| schema | 数据库的结构：有哪些表、每张表有哪些列、表和表之间怎么关联。模型必须看着它写 SQL。 |
| prompt | 每次交给模型的全部输入文字，包括 schema、题目、附加提示和指令。 |
| token | 模型处理文字的最小单位，大致相当于半个到一个英文单词。prompt 太长会超过模型能处理的上限。 |
| SFT（监督微调） | 给模型看"题目 + 标准答案"，让它模仿。 |
| LoRA | 一种省显存的微调方式，不改模型本体，只训练一小块附加参数（称为 adapter），训练完可以合并回模型。 |
| GRPO | 一种强化学习方法：同一道题让模型写多个答案，各自执行打分，鼓励比同组平均分高的写法。 |
| DPO | 另一种后训练方法：给模型看同一道题的一好一坏两个答案，拉大两者的概率差。 |
| reward（奖励） | 强化学习里给每个答案打的分。本项目里就是执行准确率。 |
| rollout | 强化学习训练时模型生成的一个候选答案。 |
| checkpoint | 训练到某一步时保存下来的模型权重。 |
| vLLM | 让模型快速批量生成文字的推理引擎，本项目用它把模型起成一个网络服务。 |
| verl | 做强化学习训练的框架。 |
| Qwen3-1.7B | 本项目用的基座模型，17 亿参数，很小。 |
| val 788 | 从 BIRD train 里按数据库整块切出来的固定验证集，788 题、3 个数据库，训练集里一道这三个库的题都没有。 |

## 一、这个项目要解决什么问题

一句话：让一个很小的模型学会写正确的 SQL，判断对错的方式是真的去执行，并且把"执行"
这件事用到训练和推理的每一环里。

为什么选这个方向：SQL 对不对可以由机器自动判定，不需要人打分。这类"奖励可以被机器验证"
的任务是强化学习最适合的场景。同时它有真实的工程难点：模型写的 SQL 不可信，不能随便跑；
官方的判分方式有漏洞，强化学习最擅长找漏洞；小模型在几十张表里找不到该用哪张表。

项目从一开始就定了几条纪律，写在 `AGENTS.md` 里，后面所有工作都受它约束：

- 训练时的奖励只能来自 BIRD train 的标准答案；
- 从 train 里切一个固定的验证集用来选模型、调参数，切法和随机种子写进配置文件；
- BIRD dev 只在最后读一次，不能用来调任何东西；
- 每一个产生指标的运行都自动追加一行到台账，记下代码版本、数据划分、样本数、解码参数；
- 没验证的东西写"待验证"，不写"已实现"；工作区有未提交改动时跑出的数字不能对外汇报。

这些纪律是这个项目和"调一调 prompt 看看分数"的根本区别，后面会看到它们好几次救了项目。

## 二、时间线：从地基到今天

### 第一阶段（8 月 7 日到 8 日）：地基，以及两次被自己推翻的结论

**读数据和渲染 schema。** BIRD 不同版本的目录名、字段名略有差异，加载器不写死路径，
按已知文件名去找。schema 直接从数据库文件里读，不读 BIRD 附带的 JSON，因为 SQL 最终是在
文件上执行的。渲染成文字有两种风格，可以选择带上每列的文字说明和样例数据行。

**只读执行沙箱。** 执行的是模型生成的、不可信的 SQL，做了三层隔离：先做文本检查，拒绝
非查询语句和多条语句；再用只读方式打开数据库；最后挂上 SQLite 自带的授权回调，除读取外
一律拒绝。另有超时和返回行数上限。为了强化学习时每步要执行几百条 SQL，做了连接复用和
结果缓存。这里的瓶颈是数据库不是显卡，这点和直觉相反。

**两套判分标准并存，这是整个项目最重要的一个设计决定。** BIRD 官方的判法是把两边的查询
结果各自去重成集合再比较。这有洞：模型漏写或多写去重，结果行数不同，官方照样判对；标准
答案本身为空的题，任何查不出东西的 SQL 都判对。处理方式不是改官方标准（那样数字就没法和
别人比），而是两套同时跑：一套一字不改复刻官方口径，对外只报这个；另一套是自己的严格
验证器，列数要一致、重复行要保留、数值归一化后比较。两者的差就是"靠漏洞拿到的分"。

**下载工具的坑。** BIRD 数据在阿里云北京，从德国拉七百多兆经常断，续传接缝对不上。
ZIP 的目录信息在文件末尾，中间坏了、末尾完好的包用标准库打开一切正常，只有解压到坏的
位置才报错，而且报错指向解压模块。修法是解压前先完整校验一遍。

**攻击面测量，以及一次反转。** 先在 mini-dev 的 500 题上把全部标准答案执行了一遍：
标准答案为空的题 0 道，含重复行 33 道（6.6%）。据此下了结论"空结果骗分这条路死了"。
第二天下载了训练集（9428 题、69 个数据库、31 GB），同样量一遍：空结果 283 道（3.0%），
重复行 487 道（5.2%），合计 8.2%。前一天的结论错了，原因是量错了对象：骗分发生在训练
过程中，奖励在训练集上算，而 mini-dev 是人工精选过的。教训是一个测量的适用范围和它的
数值一样重要。

**清洗和切分。** 训练集里 370 道题的标准答案自己就跑不出结果，另有 79 道跑得太慢，
合计 449 道剔除。剩下 8979 道切成训练 8191 道、验证 788 道。验证集按数据库整块切，
用了 image_and_language、synthea、works_cycles 三个库，训练集里一道这三个库的题都没有。
这样做是因为 BIRD 的测试集用的全是训练时没见过的数据库，验证集必须"难在同一个地方"。
切法、种子、每道题的归属都写进了 `configs/splits/train_val.json`。

**第一个真实数字。** 在 AutoDL 租了一张 4090，云上只跑 vLLM 服务，数据、判分、评测留在
本地，中间一条 SSH 隧道。未训练的 Qwen3-1.7B 在 mini-dev 500 题上：官方口径 19.80%，
严格口径 17.40%。简单题 36.5%，中等题 14.4%，困难题 8.8%。

**错误分析和被否决的提示词。** 500 题里 208 题的 SQL 根本执行不了。归类后发现 46 题
（9.2%）的失败和模型会不会写 SQL 无关：BIRD 的附加提示用 DIVIDE(A, B) 这种伪函数记号写，
模型原样抄进 SQL；还有用了 MySQL 的日期函数、Oracle 的 MINUS。于是写了第二版提示词，
明确说这些是记号、别用那些函数。在验证集上一比：原版 21.83%，新版 18.40%，新版更差。
最讽刺的是明确写了"不要用 YEAR()"，这类错误反而从 34 例翻到 69 例，小模型处理否定句
不可靠，点名等于提醒。另一条"需要时请关联表"让模型开始编造不存在的关联。方法上的教训：
一次改了四条规则，无法归因；基于推理的改进未必是改进；幸好是在验证集上试的，评测集
一次没碰。原版提示词定版，所有后续训练都用它。

顺带修了一个台账 bug：判断工作区是否干净时按固定列偏移解析 git 输出，捕获时被去掉了
首尾空白，路径整体错位一个字符，排除规则永远匹配不上。"一个宣称已经检查过的检查，
实际上什么都没检查"，这句话后面还会出现好几次。

### 第二阶段（8 月 8 日）：第一次训练，以及提升里掺的水

把 8191 道题转成对话格式，核心约束只有一条：训练时喂给模型的输入必须和评测时逐字节一致，
所以造数据直接调用评测用的同一个函数。答案必须能被评测的解析器原样读回。量了样本长度：
中位数 2954 字符，最长 14599 字符，据此定截断阈值，因为被截掉的是序列末尾，正是答案，
被截的样本会教模型"什么都不要输出"。

在 4090 上用 LoRA 训了一轮，约 30 分钟：

| 数据集 | 未训练 | SFT 后 |
|---|---:|---:|
| 验证集 788 题 | 21.83% | 33.38% |
| mini-dev 500 题 | 19.80% | 34.60% |

**提升的拆解比总分重要。** mini-dev 上 104 道由错变对、30 道由对变错。新答对的 104 道里，
53 道微调前是执行不了的（主要学会了格式和方言），51 道微调前能执行但答错（查询能力真的
变强）。大约一半一半。方言类错误几乎清零（不存在的函数 35 例到 0，两条语句 5 例到 0），
而真正的能力问题"引用不存在的列"只从 134 降到 104。

**一个和设想相反的发现。** 官方给分、严格不给分的题从 12 道涨到 25 道，全部是同一个
形状：标准答案写了去重返回 21 行，模型漏写返回 933 行，官方各自去重后判为相同。原先设想
的是模型多写去重把行压掉，真实数据里占主导的是反方向。这意味着如果用官方口径当强化学习
的奖励，模型在"要不要去重"上完全没有压力。这为后面用严格验证器当奖励提供了实测依据。

### 第三阶段（8 月 8 日到 17 日）：强化学习这条路有多难走

**奖励函数（8 月 8 日）。** 严格验证器当奖励；默认不给部分分，但留了两个开关（格式正确
给分、能执行给分），它们明显是漏洞，留着就是为了做实验量模型多快学会钻空子。每次打分的
完整记录写进独立日志，骗分率是训练中被测量的，不是事后反推。奖励函数是项目里唯一"错了
也不会报错"的部件，所以有三十多条单元测试钉死每种输出的得分。顺带纠正了一个换算：
原来按 3.3 字符一个 token 估算，拿真实记录核对后是 3.79 到 5.57，schema 里全是重复的
长标识符，分词效率高。

**24 GB 不够（8 月 9 日）。** 在 4090 上调试 GRPO，越过了配置解析、进程初始化、vLLM
初始化，走到第一次把训练侧权重同步给 vLLM 时显存耗尽：训练进程占 13.2 GB，vLLM 占
10.2 GB，只剩 93 MB。沿途还处理了三类兼容问题。决定换单卡大显存，而不是双卡，因为双卡
会引入分片、并行、通信一堆新变量。

**三处会毁掉可复现性的隐患（8 月 15 日）。** 上 GPU 前做了一次体检。第一，`.gitignore`
里写的 `data/` 本意是忽略数据目录，但它匹配任何层级叫 data 的目录，于是源码包
`src/text2sql_rlvr/data/` 从项目开始就没进过 git，别人克隆下来的仓库是坏的。第二，
提示词已经定版为原版，但推理脚本的默认值还停在被否决的新版，只要忘了显式传参，评测就
用错提示词。第三，切分后的题目丢了原始编号，导致按编号找例子会找错题。三处都修了，
修法都是"锚定"：忽略规则加根目录前缀，默认值和定版决策对齐，原始编号逐条写回。

**Blackwell 上打通（8 月 16 日）。** 换到一张 RTX 6000D，84 GB，新架构。引入的不是一张卡
而是一整套"三新叠加"：新硬件、新版 verl、新版 vLLM。踩平了十几处坑，每处都有根因：
torch 在新架构上的导入 bug，注释掉两行断言；vLLM 必须钉在 0.24.0，否则和 verl 的 LoRA
接口对不上；transformers 降到 5.5.3；flash-attn 编译不了，改 verl 一行导入用替代实现；
verl 新版把自定义奖励的配置键改了名，旧键被静默忽略；单卡要改并行度默认值；我们自己的
日志攒够 200 条才写盘，小规模跑直接丢日志。三步冒烟跑通。第一条 rollout 日志就复现了
之前预言的现象：模型返回 8212 行、标准答案 2180 行，官方给分、严格不给。

**重训 SFT、正式 GRPO（8 月 16 日）。** 数据盘丢失后 SFT 权重没了。这次没有重装训练框架，
而是写了一个约 120 行的训练脚本，直接用 transformers 和 peft 复现同样的配置，28 分钟
跑完，损失曲线形态一致。正式 GRPO 第一步实测 232 秒，按 300 步要 19 小时，停掉调整：
150 步、每题 4 个答案、关梯度检查点。4 小时 16 分跑完。

**结果是负的，然后被订正（8 月 16 到 17 日）。** 先记下的是 GRPO 后验证集 29.70%，
比 SFT 的 33.38% 低。重新核对后发现比错了对象：GRPO 是从 16 日重训的新 SFT 出发的，
而 33.38% 是 8 日那个已经丢失的旧 SFT。给真实起点补做评测：新 SFT 是 29.19%，所以 GRPO
是 +0.51 个百分点而不是下降。同时从训练日志发现 rollout 时 Qwen3 的思考模式默认是开的，
而 SFT 和评测都是关的，训练和评测的分布不一致。修正后重跑，按预设止损规则在第 10 步停：
29.31%，和起点差一道题。为什么新 SFT 没复现旧 SFT 的 33.38%，至今没有完全解释。

**用真实分词器排除截断（8 月 17 日）。** 一直有个猜测是完整 schema 太长把题目截掉了。
用 Qwen3 的真实分词器逐题计数：完整 schema 的 prompt 最长 6722 个 token，上限 8192，
没有一题超限。猜测被排除。于是问题变成：不截断，六千多 token 的无关表会不会干扰小模型。

### 第四阶段（8 月 17 日）：找到了真正有效的东西

新增三种 schema 模式：full（全部表）、linked（只看题目和附加提示做词面匹配、再补上
外键相邻的表）、oracle（直接读标准答案用了哪些表，作弊，只作诊断上界）。同一个 SFT
模型、同 200 题、同解码，只换 schema：

| schema | 官方口径 | 严格口径 |
|---|---:|---:|
| full | 33.0% | 27.0% |
| linked | 39.5% | 34.0% |
| oracle | 48.0% | 41.0% |

在完整 788 题、干净提交上复现：full 32.87%，linked 37.94%，提升 5.07 个百分点；
严格口径同步提升 4.95。逐题配对新增答对 76 题、丢掉 36 题。两种口径同向提升，说明收益
不是钻官方口径的空子。结论：对 1.7B 模型，大量无关表的干扰比上下文截断更值得优先处理。

同时把 GRPO 的奖励从严格口径改成官方口径，因为最终考试是官方口径，训练目标要和考试
对齐；严格口径改为只做监控。用 linked schema 和官方奖励重跑普通 GRPO，500 道训练题、
30 步、每题 4 个答案，在固定 200 题上选点，完整 788 题上：38.20%，比 SFT 的 37.94%
多 2 题。正式结论是"没有明确额外收益"，不包装成成功。

到这里项目做了一次收尾：README、最终报告、交接文档、简历素材。可对外的五行数字：

| 阶段 | 划分 | 题数 | 官方口径 | 严格口径 |
|---|---|---:|---:|---:|
| 未训练 | mini-dev | 500 | 19.80% | 17.40% |
| SFT | mini-dev | 500 | 34.60% | 30.00% |
| 强 SFT，全 schema | val 788 | 788 | 32.87% | 28.68% |
| 强 SFT，linked schema | val 788 | 788 | 37.94% | 33.63% |
| 官方奖励 GRPO，linked schema | val 788 | 788 | 38.20% | 33.88% |

### 第五阶段（9 月 13 日到 14 日）：错误审计与针对性数据

这一段主要由 Codex 执行，方向是"从失败案例出发构造训练数据，而不是把训练集再训一遍"。

对未训练模型在验证集 788 题上的历史输出做了全量审计：判错 616 题，其中执行失败 343 题、
能执行但结果不对 273 题。按数据库和报错分层抽了 42 题逐题看原题、提示、SQL 和执行记录。
发现一个真实的前处理 bug：没有代码块包裹的 SQL 会被提取器截到最后一个 SELECT，嵌套查询
的外层可能丢失；修复后 13 题提取结果变化，2 题由错变对。这是工程修复，不是模型提升。

也纠正了早期的两个断言：函数报错不能直接断言为提示词问题，列报错不能直接断言为不会关联
表，样例显示多个缺陷可以共存；官方和严格口径的差也不能整体叫骗分，里面有重复语义未约定、
并列、结果截断。

为比较训练侧的残余错误，固定抽了 512 道训练题准备做配对。但检查 AutoDL 实例时确认：
强 SFT 和 GRPO 的权重已经丢失，新实例的数据盘是空的。这意味着生成模型必须重训，
之前的"最好的 SFT"身份不能沿用。

然后构造了针对性训练数据。第一批 60 条、30 对，每对围绕同一场景改变实体、统计粒度或
输出要求，分字段匹配、聚合层级、输出约定三类。第二批扩到 400 条针对性数据加 150 条原始
样本回放，共 550 条，来自 50 个模板、16 个数据库。每条 SQL 都完整执行并用 Python 从原始
数据独立核算，成对的答案在保留重复行的口径下都可区分。尚未用来训练。

### 第六阶段（9 月 14 日到 15 日）：schema 选择器、两阶段和 agent 循环

这一段是本文档作者执行的，起点是一个问题：词面 linker 的召回率 99%，准确率呢？

**发现高召回是"几乎全召回"。** 重算验证集的诊断文件：linker 平均给 25.5 张表，标准答案
平均只用 1.95 张；逐题准确率 14.2%，39% 的题选出的表和全 schema 一模一样。按库拆开更
明显：在两个小库上 linker 基本是空操作，那 5 个点的提升几乎全来自 65 张表的 works_cycles。
验证集 59% 的题来自这一个库，而 BIRD 里典型的库只有 7 到 12 张表，所以验证集是"大库
特例"。单靠词面排序也到不了目标：works_cycles 上有 21% 的题至少一张标准表在词面排序
20 名以外。结论：值得训一个选表模型。

**划分和数据。** 从 66 个训练库里按表数分档留出 10 个库、1598 题给选表模型自己做验证，
其余 56 个库训练；生成模型验证集的 3 个库两边都不出现，否则两阶段成绩会失真。标签直接
从标准答案 SQL 解析出表名，不需要人工标注。目标格式是一个 JSON 表名列表。第一版每库
最多 12 题、难题优先，共 666 题；第二版全量 6593 题。

**训练与评测。** 在一张 RTX PRO 6000（96 GB）上训练，两版都是 2 轮。评测报三个数：
每题标准表全部保留的比例（漏一张这题就废）、准确率、平均选中表数。

| 评测集 | 方法 | 全保留 | 准确率 | 选中表数 |
|---|---|---:|---:|---:|
| 留出 10 库 1598 题 | 词面 linker | 98.7% | 31.0% | 8.7 |
| 留出 10 库 1598 题 | 未训练零样本 | 79.4% | 58.2% | 4.2 |
| 留出 10 库 1598 题 | 选表 v1（666 题） | 78.6% | 84.1% | 2.3 |
| 留出 10 库 1598 题 | 选表 v2（6593 题） | 78.7% | 92.0% | 2.0 |
| val 788 | 词面 linker | 98.0% | 14.2% | 25.5 |
| val 788 | 选表 v2 | 72.8% | 90.8% | 1.8 |

**为什么十倍数据没用。** v1 和 v2 在 40% 的题上答案不同，但 v1 对 v2 错 121 题、v2 对
v1 错 128 题，净变化为零；漏表的题里 65% 是纯粹少选；漏表率随标准表数陡升（2 张 17%，
3 张 42%，4 张 62%）。典型错误是属性定位：问演员性别，标准答案用单独的 gender 表，模型
给了 person 表；问员工姓名，姓名在 Person 表，模型只选了 Employee。这是"这个没见过的库里
哪张表放着这个属性"的判断，更多别的库的题补不上。机制有三层：输入缺信息（DDL 只有列名）、
监督信号太弱（"该不该再列一张"只落在一个结束符上）、贪心解码提前停。

**推理期扩展救回召回。** 模型选集并上外键一跳邻居，再并上词面前 2 的表，不用训练：

| 评测集 | 方法 | 全保留 | 准确率 | 选中表数 |
|---|---|---:|---:|---:|
| 留出 10 库 | 选表 v2 加扩展 | 94.2% | 50.9% | 4.8 |
| val 788 | 选表 v2 加扩展 | 95.7% | 31.2% | 7.8 |

对比 linker 在 val 788 上要 25.5 张表才有 98.0%。扩展依赖数据库声明的外键，没有外键的库
（public_review_platform）扩展无效。为下一版准备了两样东西但没有训练：prompt 里附上
每列的文字说明；目标改成先列出用到的每个"表.列"再列表，标签同样从标准答案自动解析。

**两阶段对照，第一批。** 生成模型的权重丢了，改用未训练的 Qwen3-1.7B 做生成模型，
val 788 上只换 schema：

| schema | 官方口径 | 严格口径 |
|---|---:|---:|
| full | 22.08% | 19.42% |
| linked | 25.25% | 22.46% |
| oracle（上界） | 31.60% | 27.92% |

形状和 SFT 时期一致。选表模型那一组的生成因为网络中断失败了，还没有数字；它的预期区间是
25.25% 到 31.60% 之间。

**agent 循环。** 实现了执行、观察、修正的最小循环：模型每轮只做一个动作，查看某张表的
定义和样例、执行一条 SQL 看结果或报错、或者提交最终答案；每题最多 4 轮；观察以对话轮次
追加，整条轨迹就是普通聊天记录，可以直接打分，也可以做后续训练的数据。没有用任何现成的
agent 框架，一百来行，全是仓库里已有的部件。选表模型没展示的表按名字列在 prompt 里，模型
可以主动查看，这样选表漏了不再是死局。本地测试通过，还没对真实模型跑。

## 三、现在的系统长什么样

运行时：

```text
问题 + 数据库
   │
   ▼
[1] 选表模型（1.7B 的一块 LoRA）：从几十张表里选出几张，外键扩展保证 95% 的题标准表齐全
   │  没选中的表按名字列出，供第 3 步查看
   ▼
[2] 生成模型（另一块 LoRA）：拿着精简后的 schema 写 SQL
   │
   ▼
[3] agent 循环（最多 4 轮）：查看表 → 执行 → 看结果或报错 → 改 → 提交
   │  只读沙箱、超时、单语句校验
   ▼
最终 SQL → 官方口径与严格口径打分 → 台账
```

训练侧：

```text
BIRD train（66 个库）
   ├─ 选表标签从标准 SQL 解析 ──────────────→ 选表 LoRA（已有两版）
   ├─ 生成模型 SFT（原始 8191 题，或加 550 条针对性数据）──→ 生成 LoRA（待重训）
   ├─ 老师模型跑同一个 agent 循环，只留执行验证通过的轨迹 ──→ 轨迹 SFT（计划）
   ├─ 学生自己跑循环，成功与失败配对 ──────────→ DPO（计划）
   └─ 执行奖励的 GRPO（已跑过，无明确收益；可选）
```

代码分布：

| 目录 | 内容 |
|---|---|
| `src/text2sql_rlvr/data/` | 读 BIRD、渲染 schema、拼 prompt、切分、造 SFT 数据、词面 linker、选表模型的数据与解析 |
| `src/text2sql_rlvr/rewards/` | 只读沙箱、结果归一化与比较、奖励函数 |
| `src/text2sql_rlvr/eval/` | 执行准确率、逐题结果、错误分析 |
| `src/text2sql_rlvr/sql/` | SQL 抽取、只读校验、词法扫描 |
| `src/text2sql_rlvr/agent.py` | 执行、观察、修正循环 |
| `src/text2sql_rlvr/ledger.py` | 追加式实验台账 |
| `scripts/` | 下载、准备、切分、造数据、生成、评测、选表模型、agent、训练、检查点导出、诊断 |
| `configs/` | 切分清单、SFT 与 GRPO 配置、选表数据清单 |
| `tests/` | 294 项单元与端到端测试，全部用临时数据库，不需要下载也不需要显卡 |
| `docs/` | 进度记录、最终报告、各运行手册、分析报告、本文 |

## 六、值得在面试里讲的坑

- 只看 mini-dev 就下结论，训练集上反过来。测量的适用范围和数值一样重要。
- 明确写"不要用 YEAR()"，这类错误翻倍。小模型处理否定句不可靠，点名等于提醒。
- 提升了 14.8 个百分点，一半是学会了格式和方言。不拆开就是虚报。
- 官方判分放过了漏写去重的 933 行答案。两套口径的差就是漏洞的度量。
- GRPO"下降了 3.68 个点"是比错了起点；rollout 时思考模式偷偷开着。强化学习的结果必须
  和它真正出发的模型比，训练和评测的分布必须一致。
- 忽略规则 `data/` 把源码包挡在 git 外面，克隆下来的仓库是坏的。
- 一直以为是 prompt 太长被截断，用真实分词器一数，一题都没超。
- 召回率 99% 是因为保留了六成的表。召回必须和准确率并排看。
- 十倍数据没提高召回，两版模型只是换着犯错。缺的是信息不是样本。
- 台账、切分清单、只增不改的进度记录，让每一个数字在一个月后还能被核对，也让"作废"
  的数字有地方明确写下来。

**Text2SQL-RLVR：以真实执行为核心的 Text-to-SQL 训练与评测系统**

### 口头介绍，三十秒
