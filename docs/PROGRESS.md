## 项目在做什么（给第一次看到这个仓库的人）

给一个自然语言问题和一个数据库，让模型写出能回答这个问题的 SQL。判断模型写得对不对，
不靠人打分，也不靠比对 SQL 文本长得像不像，而是**把模型写的 SQL 真的放到数据库上执行一遍**，
看查询结果和标准答案的结果是否一致。一致就给 1 分，不一致就给 0 分。

这个"能自动算出对错"的分数，就可以直接拿来做强化学习的奖励信号——模型自己生成一批答案，
执行一遍，对的鼓励、错的抑制，反复迭代。这类"奖励可以被机器验证"的做法叫 RLVR
（Reinforcement Learning with Verifiable Rewards）。

用的数据集是 BIRD，一个 Text-to-SQL 基准，题目来自真实的、比较脏的数据库。
基座模型是 Qwen3-1.7B，训练框架用 verl，生成用 vLLM。

计划路线：跑通数据和评测 → 有监督微调（SFT）→ 强化学习（GRPO）→ 做消融和错误分析。
详细的优先级和纪律见 `AGENTS.md`。

## 2026-08-07 · 里程碑 1：数据、评测、执行沙箱、验证器

对应 `AGENTS.md` 工作优先级里的第 1、2 步。

### 做了什么

打通了"从数据到分数"这条链路上除模型以外的全部环节，一共四块：

**读数据。** BIRD 分成 train / dev / mini-dev 三份，每份的目录名和 JSON 字段名在不同发布版本里
略有差异。现在的加载器不写死路径，而是在给定目录下按已知文件名去找，找不到时会明确报出
"我找了哪几个名字"。另外做了一个下载脚本，一条命令下载、校验、解压、验证目录结构。

**把数据库结构变成给模型看的文字。** 模型要写 SQL，得先知道有哪些表、哪些列、哪些外键。
这部分直接从 SQLite 文件里读结构，而不是读 BIRD 附带的 JSON——因为 SQL 最终是在这个文件上
执行的，以文件为准最不容易出错。渲染成文字有两种风格可选，还能选择性带上 BIRD 提供的
列含义说明和样例数据行。

**执行模型写的 SQL。** 这是最需要小心的一块，因为执行的是模型生成的、不可信的文本。
做了三层隔离：先做文本检查（拒绝非查询语句、拒绝多条语句），再用只读方式打开数据库文件，
最后挂上 SQLite 自带的授权回调，除了读取以外的动作一律拒绝。另外有超时和返回行数上限，
防止一条恶意或愚蠢的查询把整个训练卡死。

**判断答案对不对。** 见下一节，这是整个里程碑里最关键的设计。

### 为什么这么设计

**关键决定：同时保留两套判分标准，而不是"改进"官方标准。**

BIRD 官方的判分方式是：把两边的查询结果各自去重成集合，看两个集合是否相等。这个做法有洞：

- 模型写 `SELECT DISTINCT`，把本该 5 行（含重复）的答案压成 3 行，去重后两边集合相同，判对。
- 更严重的是空结果。BIRD 里有一部分题目的标准答案本身就是空的（查不到任何记录）。
  两个空集合永远相等，所以模型只要写一句永远查不出东西的 SQL，就能在**所有**这类题目上白拿分。

这两种情况都不是"答对了"，但官方标准会给分。而强化学习最擅长的事，就是找到这种拿分捷径。
这就是所谓的 reward hacking：模型没学会做题，只学会了骗分。

处理方式不是把官方标准改严——那样报出来的数字就不能和别人比了，等于自说自话。
现在的做法是**两套标准同时跑**：

- 一个严格复刻官方口径，一个字节都不改。这是对外汇报时唯一能称作 Execution Accuracy 的数字。
- 另一个是自己的严格验证器：列数要一致、重复行要保留、数值做归一化后比较。这个用来当训练奖励。

两者跑一次同时得出（反正标准答案和模型答案本来就都要执行一遍，零额外成本）。
**两个数字之间的差，就是"靠捷径拿到的分"的直接度量**，不需要另外设计实验。

**为什么行序默认不比较。** 如果标准答案里写了排序，是不是该要求模型的结果顺序也一样？
默认不要求。原因是排序键有并列值时，并列部分的先后是数据库内部决定的、不确定的，
强行比较顺序会把正确的 SQL 判错。在强化学习里，把对的判成错，比稍微宽松一点危害更大——
前者会污染训练信号。另外 BIRD 常见的"排序后取前 k 条"这种题型，取前 k 条这件事本身
就让结果集不同了，多重集比较已经能抓住。严格比较顺序的选项也实现了，将来做消融随时能开。

**为什么数值要做归一化。** 同一个正确答案，用 `COUNT` 算出来是整数 5，用 `SUM` 算出来是
小数 5.0；`0.1 + 0.2` 在计算机里等于 0.30000000000000004 而不是 0.3。这些差异跟对错无关，
所以比较前统一处理掉。但只处理这些——空值仍然不等于 0，也不等于空字符串；大整数保持精确。

**为什么执行 SQL 这件事要做性能优化。** 强化学习训练时，每一步都要为几百上千条候选答案
算奖励，每条都要执行一次 SQL。BIRD 有些数据库好几个 GB，每次重新打开的开销远超模型推理本身。
所以做了连接复用和结果缓存。这里的瓶颈是数据库，不是显卡，这一点和直觉相反。

**为什么开发环境不装 PyTorch。** 上面这些全部只依赖 Python 自带的 SQLite，不需要显卡。
所以拆成两套依赖：本机这套能跑完所有测试，训练那套只装在租来的 Linux 机器上。
好处是数据、评测、验证器这些最容易出错的逻辑，可以在自己电脑上快速迭代，不烧一分钱租卡费。

### 还没验证的

- **没有跑过任何实验，没有训练过任何模型，没有任何性能数字。** 这一条不能被误读。
- 生成脚本是通过 HTTP 调用推理服务的，用一个假的服务端测过请求格式、重试、断点续做，
  但**没有对着真实的 vLLM 服务跑过**——本机没有显卡。
- 训练侧的依赖版本**故意没有钉死**。verl 这个框架接口变动频繁，在没有实际跑通之前写下
  一组版本号，等于把猜测伪装成锁定文件。文件里写了回填流程：先在租来的机器上跑通 verl
  官方自带的例子，确认环境是活的，再回来记录实际版本。
- 上面说的两类捷径（去重、空结果）是**用构造的测试用例验证过确实会发生**，但在真实的
  BIRD 数据上占多大比例，还不知道。这个比例决定了后续"反作弊"这条线有没有东西可做。
  下载数据后跑一次 `prepare_bird.py --check-gold` 就能得到答案。
- 各划分的实际题目数量以脚本输出为准，本文不引用记忆中的数字。

## 2026-08-07 · 里程碑 2：下载工具的完整性校验

### 做了什么

给下载脚本加了压缩包完整性校验：解压之前先对整个文件做一遍校验，发现损坏就自动丢弃重下。

### 为什么这么设计

第一次实际下载时踩到了一个坑，值得记下来。

BIRD 的数据托管在阿里云北京的服务器上，从德国拉七百多兆容易断。断了以后脚本会续传，
从断点继续下载剩下的部分。但这次续传的接缝对不上，文件中间有一段是错的。

坑在于：ZIP 格式的文件目录信息存在**文件末尾**。所以一个中间损坏、末尾完好的压缩包，
用标准库打开时**完全正常**，能列出里面有哪些文件，一切看起来都对。只有真正解压到
损坏的那个位置时才会报错——而且报错信息指向解压模块，看不出是下载的问题。

原来的脚本默认"续传一定是对的"，下完直接解压，于是把一个下载问题伪装成了一个解压问题。
现在改成解压前先完整校验一遍。校验一个七百多兆的包要几十秒，值得。

顺带加了一个更细的检查：续传时核对服务器实际返回的数据范围，是否真的等于我们请求的位置。
有些中间节点会返回不一样的范围，直接追加就会悄悄损坏。

### 还没验证的

- 修复后的脚本**在真实网络上还没有成功完整跑通一次**。逻辑本身有测试覆盖
  （包括"末尾完好、中间损坏"这个特定情况），但端到端的真实下载有待确认。
- 如果阿里云那条链路反复失败，备选是 HuggingFace 上的镜像。这条路**还没有试过**，
  也不确定镜像里是否包含数据库文件本身。

### 这个坑和项目主线的关系

值得指出的一点：**"校验通过"不等于"数据正确"**，一个只检查文件末尾就宣布成功的验证器，
会让问题在几百兆之后才暴露，而且把错误归因到错误的地方。

这和这个项目要解决的核心问题是同一类。判断 SQL 对不对时，官方那套"两个集合相等就算对"
的判据，同样是一个只看表面就宣布通过的验证器——只不过被它放过去的不是损坏的字节，
而是模型的取巧行为。

## 2026-08-07 · 里程碑 3：第一次真实测量，以及由此推翻的一个计划

### 做了什么

数据下载完成，第一次在真实的 BIRD mini-dev（500 题、11 个数据库）上把全部标准答案执行了一遍，
量出了一组"在还没有任何模型的情况下就能知道"的事实。

新增的能力是**攻击面测量**：官方判分方式是把两边查询结果各自去重成集合再比较，
所以不用真正答对也能拿分的情况只有两种——标准答案本身是空的（任何查不出东西的 SQL 都匹配），
或者标准答案里含重复行（去重后就一样了）。这两类题目占多少，只看标准答案就能算出来，
不需要模型。这个数直接决定"反作弊"这条线值不值得做。

实测结果：

| 指标 | 数值 |
|---|---|
| 标准答案可执行 | 499/500（放宽到 120 秒后；有 1 条仍超时，另有 1 条要 51.7 秒） |
| 标准答案返回空结果 | 0（0.0%） |
| 标准答案含重复行 | 33（6.6%） |
| 答案只有一行 | 341（68.2%） |
| 答案只有一列 | 392（78.4%） |
| 标准答案带排序 | 88（17.6%） |

### 为什么这么设计

**先量攻击面，再决定做不做，而不是先假设它存在。** 之前的计划把"模型学会输出永远返回空的 SQL
来骗分"当作主线故事。现在测出来这条路在 mini-dev 上的攻击面是 0.0%——一条都没有。
原因很清楚：mini-dev 是从完整验证集里人工筛出的 500 条"高质量"样本，
标准答案是空的题目在筛选阶段就被剔掉了。

如果不先量这一下，就会一路做到训练结束才发现这个故事讲不出来。花几分钟执行一遍标准答案，
换掉一个可能白做两周的假设，是这个项目目前性价比最高的一次操作。

**一个之前搞混的区分：评测集的攻击面 ≠ 训练时的攻击面。** 骗分行为发生在训练过程中，
而训练时的奖励是在训练集上算的，不是在 mini-dev 上。mini-dev 的 0.0% 说明的是评测环节的事，
说明不了训练环节。训练集有九千多条、没经过同样的人工筛选，很可能是完全不同的数字。

### 还没验证的

- **训练集的攻击面完全未知。** 这是下一步必须先测的数，它决定后面的实验设计。
- 单行答案占 68%、单列答案占 78%，说明大多数题目的标准答案就是一个数或一个字符串。
  直觉上这意味着"写错的 SQL 碰巧算出对的数"的概率不低，而这比"去重骗分"严重得多，
  也更接近执行准确率这个指标的真正弱点。**但这只是推测**：这类假阳性没法只看标准答案量出来，
  必须等有了模型输出，在拿满分的样本里抽查语义是否真的等价。目前一条都还没测。
- 6.6% 这个数只是"上限"，不是"实际会发生的比例"。它说明就算模型把这条路吃满，
  也只有 6.6% 的题目能靠去重白拿分。实际会不会发生、发生多少，要等训练跑起来。
- 有 1 条标准答案在 120 秒内跑不完，另有 1 条要 51.7 秒。按训练期 5–10 秒的超时设定，
  这两条会被算作失败，代价是 0.4%。这个损耗是已知的，不要事后误判成模型的问题。

### 由此产生的计划调整

原定的"空结果骗分"主线作废。替代方案按可行性排序，尚未选定：

1. **复合奖励自身制造的攻击面。** 如果奖励函数里含有部分分项（例如"SQL 能执行不报错就给分"），
   模型会直接去薅这一项。这个攻击面是自己设计出来的，不依赖数据集碰巧提供，因此最可控：
   可以先上朴素版本，量出模型如何利用它，再修正。
2. **执行准确率的假阳性。** 见上，信息量最大，但需要判断语义等价，成本较高。
3. **去重骗分。** 6.6% 的上限，只能作为补充细节，不足以当主线。

## 2026-08-08 · 里程碑 4：训练集测量，上一个结论被自己推翻

### 做了什么

下载了训练集（9428 题、69 个数据库，解压后约 31 GB），用里程碑 3 的同一套方法量了一遍。
另外给脚本加了一个"从已保存的结果重新出报告"的开关：执行九千多条标准答案要半小时，
不该因为终端被清空就得重跑一遍。

两个划分对照：

| 指标 | mini-dev（500 题，评测用） | train（9428 题，训练用） |
|---|---|---|
| 标准答案返回空结果 | 0（0.0%） | **283（3.0%）** |
| 标准答案含重复行 | 33（6.6%） | 487（5.2%） |
| 合计可利用面 | 33（6.6%） | **770（8.2%）** |
| 标准答案自身跑不通 | 1（0.2%） | **370（3.9%）** |
| 答案只有一行 | 68.2% | 66.9% |
| 答案只有一列 | 78.4% | 79.9% |

### 为什么这么设计

**里程碑 3 的结论"空结果骗分这条路死了"是错的，原因是量错了对象。**

上一条已经指出"评测集的攻击面不等于训练集的攻击面"，但当时只有 mini-dev 的数据，
所以把一个基于评测集的观察写成了对整条路线的判决。现在训练集测完：
mini-dev 一道空结果题都没有，训练集有 283 道。差别来自人工筛选——mini-dev 是精选出来的，
训练集不是。

骗分行为发生在训练过程中，奖励在训练集上计算。所以**决定这条路线成不成立的是 3.0%，不是 0.0%**。
原计划恢复。

这件事本身值得记一笔：一个测量结果的适用范围，和它的数值同样重要。数字没错，
用错了地方就会得出反向的结论。

**顺带发现一个必须在训练前处理的问题。** 训练集里有 370 道题的标准答案自己就执行不出结果
（350 条报错、20 条超时）。这些题目无论模型怎么回答都不可能获得正奖励，在强化学习里
纯粹是噪音——既浪费生成算力，又给策略梯度贡献无意义的零奖励样本。训练前应当过滤掉，
只保留标准答案确实可执行的 9058 道。

### 还没验证的

- 8.2% 是**上限**，不是实际发生率。它说明就算模型把两条捷径都吃满，也只有 8.2% 的题目
  能在没答对的情况下拿到奖励。模型会不会真的学到、学到什么程度，只有训练跑起来才知道。
- "过滤掉标准答案跑不通的题目"这个处理**还没有实现**，目前只是结论。
- 单行答案约 67%、单列约 80%，两个划分一致。由此推测的"写错的 SQL 碰巧算出对的数"
  这类假阳性，**仍然一条都没测过**，需要模型输出之后才能抽查。
- 训练集的超时是按 30 秒上限统计的。若按训练期 5–10 秒的设定，被判失败的题目会更多，
  具体多少还没量。

## 2026-08-08 · 里程碑 5：清理训练集，并切出验证集

### 做了什么

把原始的 9428 道训练题，处理成一份能直接用于训练的数据。两件事：

**扔掉坏题。** 449 道题被排除：370 道的标准答案本身执行不出结果（报错或超时），
另有 79 道虽然能跑通，但耗时超过训练时准备使用的 10 秒上限。

**切出验证集。** 剩下的 8979 道分成训练用 8191 道、验证用 788 道。

| | 题数 | 标准答案空结果 | 含重复行 | 合计可利用面 |
|---|---|---|---|---|
| 训练 | 8191 | 265（3.2%） | 448（5.5%） | 713（8.7%） |
| 验证 | 788 | 10（1.3%） | 34（4.3%） | 44（5.6%） |

验证集用了 3 个完整的数据库（image_and_language、synthea、works_cycles），
训练集里一道这些库的题都没有。

### 为什么这么设计

**为什么扔掉标准答案跑不通的题。** 这类题目模型无论怎么回答都拿不到分。
在强化学习里，同一道题会一次生成多个候选答案，通过它们之间的分数差异来判断哪个更好。
如果所有候选都是零分，这道题就提供不了任何有用信息，白白消耗生成算力。
留着它们不会让结果变错，但会让训练变慢，还会让"平均奖励"这个观察指标失真。

**为什么验证集要按数据库整块切，而不是随机抽题。** 验证集的用途是挑选模型和超参数，
它必须能预测最终在测试集上的表现。BIRD 的测试集用的是 11 个训练集里**完全没出现过**的
数据库——也就是说，测试的是模型面对**没见过的数据库结构**时的能力。

如果验证集是从训练题里随机抽的，那验证题所属的数据库在训练时已经被模型见过成百上千次了。
这样测出来的分数会明显偏高，用它挑出来的模型到了测试集上可能反而更差。
按数据库整块切开，验证集才和测试集"难在同一个地方"。

代价是验证集大小不好控制：数据库有大有小，目标是 500 道，实际切出来 788 道。
这是整块切分固有的，不是 bug。

**为什么切分方式要写进配置文件并纳入版本管理。** 随机种子、筛选阈值、以及最终每道题
归属哪一边，全部记录在 `configs/splits/train_val.json` 里（约 85 KB，已提交）。
生成出来的题目文件本身不提交，因为它们可以从这份记录完全重建。
这样任何一个后续结果，都能追溯到它是在哪一份数据上得到的。

### 还没验证的

- 这份数据**还没有被任何训练使用过**。切分是否合理、验证集分数是否真能预测测试集分数，
  都要等真正训练之后才知道。
- 79 道"太慢"的题是按 10 秒阈值排除的，而记录下来的耗时是多线程并行测量的，
  包含了相互竞争的开销。单独跑可能远快于记录值，也就是说这个筛选偏保守，
  可能多扔了一些本来能用的题。目前认为宁可多扔：训练时超时会让整道题变成无效样本。
- 验证集只覆盖 3 个数据库。数据库数量少意味着验证分数的波动会比较大，
  换一个随机种子切出来的验证集，分数可能有可观差异。这个波动幅度**还没有测过**。
- 训练集上 8.7% 的可利用面仍然只是上限，模型实际会不会去利用、利用多少，尚未验证。

## 2026-08-08 · 里程碑 6：第一个真实分数，以及它里面掺的水

### 做了什么

在 AutoDL 租的一张 4090 上把 Qwen3-1.7B 跑起来，让它在完全没有训练的情况下做完
mini-dev 的 500 道题，得到项目的第一个真实数字。

云上只跑模型服务，数据、判分、评测全部留在本地，中间用一条 SSH 隧道连通。
这样不必上传三个多 G 的数据库，也不必在云上部署本项目。

**基线结果（Qwen3-1.7B，未训练，mini-dev 500 题）：**

| 指标 | 数值 |
|---|---|
| 官方口径准确率 | **19.80%** |
| 自家严格口径 | 17.40% |
| 简单题 | 36.49% |
| 中等题 | 14.40% |
| 困难题 | 8.82% |

### 为什么这么设计

**紧接着做了错误分析，结果发现这个分数偏低，而且偏低的一部分原因在我。**

500 题里有 208 题的 SQL 根本执行不了，占 41.6%。把报错信息归类之后，
这 208 个失败分成性质完全不同的两类：

| 错误原因 | 数量 | 性质 |
|---|---|---|
| 引用了不存在的列 | 135 | 模型真的不会：该关联两张表的时候没关联 |
| 用了 DIVIDE / SUBTRACT | 19 | **提示词的问题** |
| 用了 YEAR / MONTH / AGE | 15 | 方言混淆 |
| MINUS 等语法错误 | 12 | 方言混淆 |
| 一次输出了两条语句 | 5 | 未遵守输出约定 |

第二组特别值得说。BIRD 给每道题附带一段"外部知识"提示，这段提示是用
`DIVIDE(A, B)`、`SUBTRACT(A, B)` 这种伪函数记号写的。模型把这个记号原样抄进了 SQL——
但 SQLite 里没有叫 DIVIDE 的函数。**这不是模型不会写 SQL，是提示词没说清楚那是记号。**

同理，YEAR()、MONTH() 是 MySQL 的函数，MINUS 是 Oracle 的语法，SQLite 都没有。
原来的提示词只说了一句"写 SQLite 查询"，显然不够。

**合计 46 题（占全部 500 题的 9.2%）的失败与模型会不会写 SQL 无关。**
相对 19.8% 的基线，这个量级不能忽略。

**为什么这必须处理，而不是留着看起来更好看。** 如果不修，后续的有监督微调一定会顺带
教会模型这些方言常识，于是"训练带来的提升"里会掺进一大块其实只是"告诉了它用的是哪种数据库"。
最后报出来的提升幅度就是虚的。基线应当代表"模型在一个合理提示词下的真实水平"，
而不是"模型被一个没说清楚的提示词拖累后的水平"。

**为什么保留了旧版提示词。** 提示词改成了可选版本（v1 / v2），v1 原样保留。
上面 19.80% 这个数是在 v1 下得到的，保留 v1 才能让它一直可复现。
每次运行会把用了哪个版本记进实验台账。

**顺带修了一个会让告警失效的问题。** 实验台账文件本身是纳入版本管理的，而每次运行都会
往里追加一行。于是从第二次运行开始，"工作区有未提交改动"这个告警必然触发，
久而久之就没人看了。现在检查时会忽略台账文件自身的改动。

### 还没验证的

- **v2 提示词有没有用，完全没有验证。** 它是根据错误分析写出来的假设，还没跑过。
- **有一个方法上的问题必须写明：上面这套错误分析是在 mini-dev 上做的，而 mini-dev 是评测集。**
  严格按照本项目的数据划分纪律，评测集不应参与任何调整决策。因此接下来的做法是：
  先在验证集（从训练集切出、数据库与训练集不重叠的那 788 道）上确认同样的失败模式存在、
  并确认 v2 确实改善了它，把提示词定死，然后才重新测一次 mini-dev。
  最终会同时报出 v1 和 v2 两个基线，并说明差异来自哪里。
- 135 题"引用了不存在的列"被归类为模型自身能力不足，但**没有逐条人工确认过**。
  其中可能混有提示词渲染方式导致的问题（例如外键关系呈现得不够显眼）。
- 生成时只有 4/500 触及长度上限，所以当前的输出长度设置不是瓶颈。这一条是确认过的。
- 模型在拿到满分的那些题里，有多少是"SQL 写错了但数字碰巧对"，仍然一条都没抽查过。

## 2026-08-08 · 里程碑 7：提示词改动在验证集上被否决

### 做了什么

里程碑 6 根据错误分析写了一版新提示词（v2），在验证集上和原版（v1）对比，各跑 788 道题。

**结果是 v2 更差。**

| | v1（原版） | v2（新版） |
|---|---|---|
| 官方口径准确率 | **21.83%** | 18.40% |
| 严格口径 | 19.54% | 16.37% |
| 答对题数 | 172 | 145 |

v2 相比 v1，有 23 道由错变对，但有 50 道由对变错。

### 为什么会这样

把两次的报错分类逐项对比，能看清楚每条规则各自干了什么：

| 错误类型 | v1 | v2 | 变化 |
|---|---|---|---|
| 引用了不存在的列 | 263 | 231 | −32 |
| **用了不存在的函数** | 34 | **69** | **+35** |
| 语法错误 | 26 | 16 | −10 |
| 列名有歧义 | 8 | 19 | +11 |

**最讽刺的一条：我明确写了"不要用 YEAR()、MONTH()、DATEDIFF()、MINUS"，
结果这类错误几乎翻倍。** 在提示词里点名一个东西，哪怕是让它别用，也等于把这个词
放进了模型的视野里。小模型处理否定句本来就不可靠，于是"别用 YEAR"被读成了"用 YEAR"。

**另一条"需要时请关联表"也起了反效果。** 引用不存在的列确实少了 32 例，
但列名歧义多了 11 例，而且抽查发现模型开始**编造并不存在的关联**：
原本一条简单查询就能答对的题，v2 硬加了一个 JOIN，然后引用了被关联表上根本没有的列。
它被推着去做一件它做不好的事。

**方法上的教训比这两条规则本身重要：**

第一，**一次改了四条规则，所以无法归因。** 现在只能说"这一版整体更差"，
没法说哪条有用、哪条有害。正确做法是一次只改一条。

第二，**基于推理写出来的改进，未必是改进。** v2 的每条规则都有实测数据支撑，
推理链条也说得通，结果仍然是负的。

第三，**这正是验证集存在的意义。** 这次对比全程在验证集上进行，评测集一次都没碰。
如果当初图省事直接在评测集上调提示词，不仅会调出一个更差的版本，还会污染最终数字。
一次约二十分钟、几块钱的验证，换掉一个会让基线下降 3.4 个百分点的改动。

### 结论

**保留 v1 作为定版提示词。** 后续的有监督微调和强化学习全部使用 v1，
里程碑 6 报出的 mini-dev 基线 19.80% 继续有效，不需要重测。

v2 保留在代码中并保留其测试，因为它是一个有据可查的负面结果。

### 顺带修掉的一个真 bug

里程碑 6 说"修好了台账文件导致的误报"，**其实没修好**，这次运行又报了一次才发现。

原因是解析 git 状态输出时按固定列偏移取文件路径，而输出在捕获时被做了一次
去除首尾空白的处理，恰好吃掉了状态码前面的那个空格，于是所有路径整体错位一个字符
（`results/...` 被读成了 `esults/...`），排除规则永远匹配不上。

现在改为不再自己解析，直接让 git 用 pathspec 把台账文件排除掉。
新增的测试会真的建一个临时 git 仓库，验证三件事：只改台账时不算脏、
不加豁免时确实算脏、改了源码时仍然算脏。

这个 bug 本身很小，但它属于本项目反复出现的同一类问题：
**一个宣称"已经检查过"的检查，实际上什么都没检查。**

### 还没验证的

- v2 的四条规则里，是否有某一条单独使用时是有益的，**没有测过**。
  考虑到时间成本，目前不打算继续拆开测。
- BIRD 提示文本里的伪函数记号（DIVIDE、SUBTRACT）确实造成了 v1 中 34 例函数错误里的一部分，
  这个现象是真实的，但**目前没有找到能在不引起反效果的前提下修掉它的说法**。
- 验证集只覆盖 3 个数据库，788 道题。两个版本 3.4 个百分点的差距是否超出该验证集本身的
  波动范围，**没有测过**（例如换随机种子重新切分、或做自助重采样）。目前按"差距明显、
  方向一致（50 变错 vs 23 变对）"接受这个结论。

## 2026-08-08 · 里程碑 8：SFT 训练数据与配置（尚未训练）

### 做了什么

把 8191 道过滤后的训练题，转成可以直接喂给训练框架的对话格式数据，
并写好了 LoRA 微调的配置和操作手册。**训练本身还没有跑。**

产出：

- `data/processed/sft_train.jsonl`——8191 条，覆盖 66 个数据库
- `configs/sft/dataset.json`——这份数据是怎么生成的（提示词配置、长度统计、代码版本）
- `configs/sft/qwen3_1.7b_lora.yaml`——训练配置
- `docs/sft-runbook.md`——分步操作手册

### 为什么这么设计

**核心约束只有一条：训练时喂给模型的输入，必须和评测时完全一致。**

如果两者有差异，模型学会的是一种它以后再也见不到的输入格式，训练出来的分数就不说明任何问题。
所以生成训练数据时，提示词不是另外拼一遍，而是直接调用评测脚本用的同一个函数、
传入同一份配置对象。测试里有一条专门断言这件事：训练样本去掉最后一轮之后，
必须和生成脚本发出去的消息完全相等。

同理，答案部分必须能被评测用的解析器原样读回来。测试覆盖了包含分号、反引号、
多行等几种写法的往返一致性。

**还有一层框架加的模板，是这一步真正的风险。** 上面保证的是消息内容一致，
但把 system / user / assistant 三段拼成一个字符串的规则，是训练框架和推理引擎各自加的。
Qwen3 的模板还可能自动插入思考块。训练时插了、推理时没插（或反过来），
模型学的格式就和评测要的对不上。手册里第 5 步专门用一条命令验证这件事，
在正式训练之前做。

**为什么先只跑一个 epoch。** 先训一轮、评一次、再决定要不要第二轮，
而不是先付两轮的钱再发现一轮就够。这和前面几个里程碑是同一个原则：
先量，再决定。

**长度截断的处理。** 实测样本长度中位数 2954 字符，最长 14599 字符（约 4400 token）。
按不同截断阈值统计会有多少样本被截：2048 截掉 12.0%，4096 截掉 3.6%，6144 起为零。
配置取 8192，留出字符估算与真实分词器之间的误差余量。

之所以专门量这个：截断砍掉的是序列末尾，而末尾正是答案。被截的样本会教模型
"什么都不要输出"。这类问题不会报错，只会表现为训练完效果莫名其妙地差。

### 还没验证的

- **没有训练过，没有任何 SFT 结果。** 配置里的每个超参都是有依据的起点，不是实测最优。
- `configs/sft/qwen3_1.7b_lora.yaml` **从未被任何框架加载过**。其中两处已显式标注
  `VERIFY`：模板名称在当前版本是否存在、关闭思考模式的参数名是否正确。
- 训练框架与推理引擎的对话模板是否真的一致，**尚未验证**，手册第 5 步就是做这件事。
  这是本阶段唯一的高风险项。
- 一个 epoch 是否足够、LoRA 秩取 32 是否合适、学习率 1e-4 是否合适，全部未验证。
- 训练耗时按 4090 估算为 2–4 小时，**属于估算，未实测**。

### 一个需要提前说清楚的解读问题

即使 SFT 带来明显提升，这个提升也不全是"模型更懂怎么查数据了"。
里程碑 6 量过：基线里有 9.2% 的题纯粹败在方言和输出格式上（把 BIRD 提示里的伪函数记号
当成真函数抄进 SQL、用了 MySQL 的日期函数等）。SFT 一定会顺带修掉这一类。

所以评测报告里"执行失败数量下降了多少"这一项必须单独看，它衡量的是格式问题被修掉的部分。
把这部分和真正的能力提升混在一起报，就是虚报。

## 2026-08-08 · 里程碑 9：SFT 完成，提升拆解，以及验证器口径差扩大一倍

### 做了什么

在一张 4090 上用 LoRA 对 Qwen3-1.7B 做了一轮监督微调（8191 道题，约 30 分钟），
先在验证集评测，再在 mini-dev 评测。

| 数据集 | 未训练 | SFT 后 | 提升 |
|---|---|---|---|
| 验证集（788 题，数据库与训练集不重叠） | 21.83% | **33.38%** | +11.55 |
| mini-dev（500 题） | 19.80% | **34.60%** | +14.80 |

### 提升是从哪来的

**这个拆解比总分重要。** mini-dev 上共有 104 道由错变对、30 道由对变错，净增 74 道。
把新答对的 104 道按"微调前是哪种失败"分开：

| 微调前的状态 | 题数 | 意味着 |
|---|---|---|
| SQL 根本执行不了 | 53 | 主要是学会了格式和方言 |
| 能执行但答案不对 | 51 | 查询能力确实变强了 |

**大约一半一半。** 报"提升了 14.8 个百分点"是事实，但把它整个说成"模型更会查数据了"就是虚报。

执行失败从 207 降到 107，其中方言类几乎清零：

| 失败原因 | 未训练 | SFT 后 |
|---|---|---|
| 用了不存在的函数 | 35 | **0** |
| 语法错误 | 16 | 1 |
| 聚合函数误用 | 7 | **0** |
| 一次输出两条语句 | 5 | **0** |
| 引用不存在的列 | 134 | 104 |

前四行合计 63 例降到 1 例——这正是里程碑 6 判断的"与会不会写 SQL 无关的损失"，
微调顺手就修掉了。而"引用不存在的列"这个真正的能力问题，只从 134 降到 104。

### 一个原先设想反了的发现

**官方口径给分、严格口径不给分的题目，从 12 道涨到 25 道，翻了一倍。**

25 道全部是同一个原因：行数对不上。抽样查看后，模式高度一致，但方向和原先设想的相反：

| | 标准答案 | 模型预测 |
|---|---|---|
| 例 1 | `SELECT DISTINCT ...`，21 行 | 漏掉 DISTINCT，**933 行** |
| 例 2 | `SELECT DISTINCT ...`，1 行 | 漏掉 DISTINCT，3 行 |
| 例 3 | `SELECT DISTINCT ...`，4 行 | 漏掉 DISTINCT，45 行 |

**是标准答案带 DISTINCT，模型漏写了。** 官方口径把两边各自去重再比较，
于是 933 行和 21 行被判为相同，照给满分。

之前一直设想的是相反的情形——模型多写 DISTINCT 把重复行压掉。真实数据里占主导的是这一侧。
而且微调之后模型使用 DISTINCT 的次数反而从 15 次降到 9 次。

**这件事对下一步的意义很直接。** 如果用官方口径当强化学习的奖励，
模型在"要不要去重"这件事上**完全没有压力**：返回 933 行和返回正确的 21 行，得分一模一样。
强化学习会放大一切无压力的方向。这为"用严格验证器当奖励"提供了实测依据，
而不再只是一个设计上的主张。

### 还没验证的

- 只训练了一个 epoch。第二个 epoch 是否还有收益**没有测过**。
  考虑到一轮仅需半小时，这不是成本问题，而是判断下一步优先级的问题：
  当前决定是不再加轮次，直接进入强化学习。
- 30 道由对变错的题**没有逐条看过**，不清楚是随机波动还是某类系统性退化。
- 那 25 道"官方给分严格不给分"的题只抽查了 3 条，模式一致，但**没有全部核对**。
- "查询能力真的变强了"的那 51 道，判定依据是"微调前能执行但答错"，
  **没有人工确认这 51 道的 SQL 语义是否真的正确**，其中可能有蒙对的。
- 模型在拿到满分的题目里，有多少是"SQL 写错了但结果碰巧对"，**仍然一条都没抽查过**。
  这是里程碑 3 就记下的待办，至今未做。

## 2026-08-08 · 里程碑 10：GRPO 的奖励函数与训练数据（尚未训练）

### 做了什么

写完了强化学习需要的全部本地部分：奖励函数、训练数据、运行脚本、结果分析工具。
**训练本身还没有跑。**

强化学习和监督微调的区别在于：监督微调是照着标准答案抄，写法不同就算错；
强化学习是同一道题让模型写 8 个不同答案，各自拿到数据库上执行，
按执行结果对错给分，再鼓励高于本组平均分的写法。
所以模型可以写出与标准答案完全不同、但结果一样正确的 SQL，照样得满分。

### 为什么这么设计

**奖励用严格验证器，不用官方口径。这是里程碑 9 的实测结论直接决定的。**

微调后有 25 道题官方给分而严格不给，全部是同一个形状：标准答案写了去重返回 21 行，
模型漏写返回 933 行，官方口径两边各自去重后判为相同。
如果用官方口径当奖励，模型在"要不要去重"上完全不受约束——两种写法得分一样。
强化学习会放大一切不受约束的方向。

这条以前是设计上的主张，现在是有数据支撑的决定。

**默认不给部分分，但把口子留着当实验。**

奖励函数里有两个开关：一个奖励"输出格式正确"，一个奖励"SQL 能执行不报错"。
默认都是零。第二个尤其明显是漏洞——`SELECT 1` 就能执行，完全不读数据库。

留着它不是疏忽，**它就是实验本身**：打开，量模型多快找到这个漏洞、输出退化成什么样；
关掉，再量一次。两种配置都通过环境变量控制，不需要改代码，因此不会出现
"改了忘了改回来"这种事故。

**每次打分的完整记录写进一个独立的日志文件。**

不依赖训练框架怎么处理返回值——不管装的是哪个版本，每一次 rollout 的判定
（得分、严格口径对错、官方口径对错、是否读了表、返回几行）都落到我们自己控制的文件里。
骗分率是**训练过程中被测量的**，不是事后从检查点反推的。

**奖励函数是这个项目唯一"错了也不会报错"的部件。**
奖励算错不会崩，只会给出平滑的曲线、上升的均值，和一个学歪了的模型。
所以它有 30 多条单元测试，逐一钉死每种输出形状的得分：正确答案 1 分；
写法不同但结果正确也是 1 分；`SELECT 1` 零分；漏写去重零分（同时记录"官方本会给分"）；
企图写库的直接拒绝。

### 顺带修正了一个自己的估算错误

之前用"3.3 字符 = 1 token"把字符数换算成 token 数，用来定训练的长度上限。
拿真实生成记录核对后发现这个比值实际在 3.79 到 5.57 之间——
schema 文本里全是重复的长标识符，分词效率比自然语言高得多，
最极端的一个 65 张表的库，36993 个字符只有 6731 个 token，
而原来的估算会算成 11210。

换算系数已按实测改成 3.6（取偏保守的一端：高估 token 只是多占一点显存，
低估会导致样本被静默丢弃）。而强化学习的长度上限直接用实测值定：
1288 次真实生成中最长 6731 token，取 8192。

顺带确认了一件事：之前所有评测的生成请求**零失败**，
没有任何一道题因为提示词过长被丢掉，此前的分数都是有效的。

### 还没验证的

- **没有训练过，没有任何强化学习结果。**
- verl 的配置项名称**全部未经验证**，这是最可能卡住的地方。
- 单卡 24 GB 显存能否放下"训练 + 生成"同时进行，**未验证**。
- 超参数（学习率 1e-6、每题 8 个答案、KL 系数 0.001 等）是有依据的起点，非实测最优。
- 耗时估算为 3–7 小时，**属于估算**。上一次估算错了 4 到 8 倍，这次同样不可信，
  以冒烟跑出的单步耗时为准。
- **反作弊实验尚未进行。** 目前只有"漏洞存在且可测量"的工具，
  没有"模型确实会去利用它"的证据。这是下一个里程碑要拿到的东西。
- 模型在拿到满分的题里有多少是"SQL 写错但结果碰巧对"，**从里程碑 3 记到现在仍未抽查**。

## 2026-08-09 · 里程碑 11：GRPO 初始化走到权重同步，24 GB 单卡容量不足

### 做了什么

在 AutoDL 单卡 RTX 4090 24 GB 上实际调试了 GRPO smoke。使用的 verl commit 是
`4a2cba76f7f605d2b9f56e640faaeaa71c2c7f71`。这次已经越过配置解析、Ray worker
初始化和 vLLM 初始化，最终走到第一次把训练侧 actor 权重同步给 vLLM。

沿途确认并处理了三类兼容问题：旧版任务运行器绕过缺失的 `transfer_queue`；
没有 FlashAttention2 时改用 PyTorch `sdpa`；AutoDL 容器不支持 vLLM 睡眠模式所需的
cuMem 接口时，同时关闭 `enable_sleep_mode` 和 `free_cache_engine`。

关闭睡眠模式后，LoRA 的 IPC 注入路径在 vLLM `add_lora()` 内因张量维度不匹配失败。
设置 `lora.merge=True` 后，日志确认程序改走“先把 LoRA 合入基础权重，再同步普通权重”的路径。

最后一次真实失败发生在这条合并路径的首次权重同步：actor/FSDP 进程约占 13.21 GiB，
vLLM 进程约占 10.20 GiB，24 GB 卡只剩 93 MiB；复制 `lm_head.weight` 还需约 1.16 GiB，
因此 OOM。reserved-but-unallocated 只有约 108 MiB，这不是显存碎片造成的假象。

关机前生成了 `/root/autodl-tmp/handoff_20260809.tar.gz` 并执行 `sync`。
截图确认合并后的 SFT 模型约 3.3 GB、RL 数据约 3.3 MB；但
`/root/autodl-tmp/bird` 不存在。旧实例目前已关机但未释放。

### 为什么这么设计

cuMem 问题需要同时关两个开关，因为它们控制不同阶段：`enable_sleep_mode` 决定 vLLM
初始化时是否启用该能力，`free_cache_engine` 只控制后续是否调用释放。此前只建议关闭
`free_cache_engine` 是错误的，已经在运行手册和脚本中订正。

下一步优先换单卡 48 GB，而不是立即双卡。双卡会额外引入 FSDP 分片、张量并行和 NCCL
通信等变量；现在的目标只是先证明单机链路可以完成训练 step，单张大显存卡更容易隔离问题。

smoke 脚本收缩到 batch 2、每题 2 个 rollout，并计划使用 CPU offload、eager 模式和
`max_num_seqs=4`。这不是为了正式训练效果，而是降低第一次端到端验证的显存和并发压力；
smoke 通过后再逐项恢复吞吐配置。

### 还没验证的

- **仍未完成任何 GRPO 训练 step。** 没有 rollout、reward、反向传播或 GRPO checkpoint。
- `lora.merge=True` 只确认切换了代码路径，没有在足够显存的卡上完成权重同步。
- 单卡 48 GB 是否足够、保守 smoke 参数是否能跑通，尚未验证。
