## 项目在做什么（给第一次看到这个仓库的人）

给一个自然语言问题和一个数据库，让模型写出能回答这个问题的 SQL。判断模型写得对不对，
不靠人打分，也不靠比对 SQL 文本长得像不像，而是**把模型写的 SQL 真的放到数据库上执行一遍**，
看查询结果和标准答案的结果是否一致。一致就给 1 分，不一致就给 0 分。

这个"能自动算出对错"的分数，就可以直接拿来做强化学习的奖励信号——模型自己生成一批答案，
执行一遍，对的鼓励、错的抑制，反复迭代。这类"奖励可以被机器验证"的做法叫 RLVR
（Reinforcement Learning with Verifiable Rewards）。

用的数据集是 BIRD，一个 Text-to-SQL 基准，题目来自真实的、比较脏的数据库。
基座模型是 Qwen3-1.7B，训练框架用 verl，生成用 vLLM。

计划路线：跑通数据和评测 → 有监督微调（SFT）→ 强化学习（GRPO）→ 做消融和错误分析。
详细的优先级和纪律见 `AGENTS.md`。

## 2026-08-07 · 里程碑 1：数据、评测、执行沙箱、验证器

对应 `AGENTS.md` 工作优先级里的第 1、2 步。

### 做了什么

打通了"从数据到分数"这条链路上除模型以外的全部环节，一共四块：

**读数据。** BIRD 分成 train / dev / mini-dev 三份，每份的目录名和 JSON 字段名在不同发布版本里
略有差异。现在的加载器不写死路径，而是在给定目录下按已知文件名去找，找不到时会明确报出
"我找了哪几个名字"。另外做了一个下载脚本，一条命令下载、校验、解压、验证目录结构。

**把数据库结构变成给模型看的文字。** 模型要写 SQL，得先知道有哪些表、哪些列、哪些外键。
这部分直接从 SQLite 文件里读结构，而不是读 BIRD 附带的 JSON——因为 SQL 最终是在这个文件上
执行的，以文件为准最不容易出错。渲染成文字有两种风格可选，还能选择性带上 BIRD 提供的
列含义说明和样例数据行。

**执行模型写的 SQL。** 这是最需要小心的一块，因为执行的是模型生成的、不可信的文本。
做了三层隔离：先做文本检查（拒绝非查询语句、拒绝多条语句），再用只读方式打开数据库文件，
最后挂上 SQLite 自带的授权回调，除了读取以外的动作一律拒绝。另外有超时和返回行数上限，
防止一条恶意或愚蠢的查询把整个训练卡死。

**判断答案对不对。** 见下一节，这是整个里程碑里最关键的设计。

### 为什么这么设计

**关键决定：同时保留两套判分标准，而不是"改进"官方标准。**

BIRD 官方的判分方式是：把两边的查询结果各自去重成集合，看两个集合是否相等。这个做法有洞：

- 模型写 `SELECT DISTINCT`，把本该 5 行（含重复）的答案压成 3 行，去重后两边集合相同，判对。
- 更严重的是空结果。BIRD 里有一部分题目的标准答案本身就是空的（查不到任何记录）。
  两个空集合永远相等，所以模型只要写一句永远查不出东西的 SQL，就能在**所有**这类题目上白拿分。

这两种情况都不是"答对了"，但官方标准会给分。而强化学习最擅长的事，就是找到这种拿分捷径。
这就是所谓的 reward hacking：模型没学会做题，只学会了骗分。

处理方式不是把官方标准改严——那样报出来的数字就不能和别人比了，等于自说自话。
现在的做法是**两套标准同时跑**：

- 一个严格复刻官方口径，一个字节都不改。这是对外汇报时唯一能称作 Execution Accuracy 的数字。
- 另一个是自己的严格验证器：列数要一致、重复行要保留、数值做归一化后比较。这个用来当训练奖励。

两者跑一次同时得出（反正标准答案和模型答案本来就都要执行一遍，零额外成本）。
**两个数字之间的差，就是"靠捷径拿到的分"的直接度量**，不需要另外设计实验。

**为什么行序默认不比较。** 如果标准答案里写了排序，是不是该要求模型的结果顺序也一样？
默认不要求。原因是排序键有并列值时，并列部分的先后是数据库内部决定的、不确定的，
强行比较顺序会把正确的 SQL 判错。在强化学习里，把对的判成错，比稍微宽松一点危害更大——
前者会污染训练信号。另外 BIRD 常见的"排序后取前 k 条"这种题型，取前 k 条这件事本身
就让结果集不同了，多重集比较已经能抓住。严格比较顺序的选项也实现了，将来做消融随时能开。

**为什么数值要做归一化。** 同一个正确答案，用 `COUNT` 算出来是整数 5，用 `SUM` 算出来是
小数 5.0；`0.1 + 0.2` 在计算机里等于 0.30000000000000004 而不是 0.3。这些差异跟对错无关，
所以比较前统一处理掉。但只处理这些——空值仍然不等于 0，也不等于空字符串；大整数保持精确。

**为什么执行 SQL 这件事要做性能优化。** 强化学习训练时，每一步都要为几百上千条候选答案
算奖励，每条都要执行一次 SQL。BIRD 有些数据库好几个 GB，每次重新打开的开销远超模型推理本身。
所以做了连接复用和结果缓存。这里的瓶颈是数据库，不是显卡，这一点和直觉相反。

**为什么开发环境不装 PyTorch。** 上面这些全部只依赖 Python 自带的 SQLite，不需要显卡。
所以拆成两套依赖：本机这套能跑完所有测试，训练那套只装在租来的 Linux 机器上。
好处是数据、评测、验证器这些最容易出错的逻辑，可以在自己电脑上快速迭代，不烧一分钱租卡费。

### 还没验证的

- **没有跑过任何实验，没有训练过任何模型，没有任何性能数字。** 这一条不能被误读。
- 生成脚本是通过 HTTP 调用推理服务的，用一个假的服务端测过请求格式、重试、断点续做，
  但**没有对着真实的 vLLM 服务跑过**——本机没有显卡。
- 训练侧的依赖版本**故意没有钉死**。verl 这个框架接口变动频繁，在没有实际跑通之前写下
  一组版本号，等于把猜测伪装成锁定文件。文件里写了回填流程：先在租来的机器上跑通 verl
  官方自带的例子，确认环境是活的，再回来记录实际版本。
- 上面说的两类捷径（去重、空结果）是**用构造的测试用例验证过确实会发生**，但在真实的
  BIRD 数据上占多大比例，还不知道。这个比例决定了后续"反作弊"这条线有没有东西可做。
  下载数据后跑一次 `prepare_bird.py --check-gold` 就能得到答案。
- 各划分的实际题目数量以脚本输出为准，本文不引用记忆中的数字。

## 2026-08-07 · 里程碑 2：下载工具的完整性校验

### 做了什么

给下载脚本加了压缩包完整性校验：解压之前先对整个文件做一遍校验，发现损坏就自动丢弃重下。

### 为什么这么设计

第一次实际下载时踩到了一个坑，值得记下来。

BIRD 的数据托管在阿里云北京的服务器上，从德国拉七百多兆容易断。断了以后脚本会续传，
从断点继续下载剩下的部分。但这次续传的接缝对不上，文件中间有一段是错的。

坑在于：ZIP 格式的文件目录信息存在**文件末尾**。所以一个中间损坏、末尾完好的压缩包，
用标准库打开时**完全正常**，能列出里面有哪些文件，一切看起来都对。只有真正解压到
损坏的那个位置时才会报错——而且报错信息指向解压模块，看不出是下载的问题。

原来的脚本默认"续传一定是对的"，下完直接解压，于是把一个下载问题伪装成了一个解压问题。
现在改成解压前先完整校验一遍。校验一个七百多兆的包要几十秒，值得。

顺带加了一个更细的检查：续传时核对服务器实际返回的数据范围，是否真的等于我们请求的位置。
有些中间节点会返回不一样的范围，直接追加就会悄悄损坏。

### 还没验证的

- 修复后的脚本**在真实网络上还没有成功完整跑通一次**。逻辑本身有测试覆盖
  （包括"末尾完好、中间损坏"这个特定情况），但端到端的真实下载有待确认。
- 如果阿里云那条链路反复失败，备选是 HuggingFace 上的镜像。这条路**还没有试过**，
  也不确定镜像里是否包含数据库文件本身。

### 这个坑和项目主线的关系

值得指出的一点：**"校验通过"不等于"数据正确"**，一个只检查文件末尾就宣布成功的验证器，
会让问题在几百兆之后才暴露，而且把错误归因到错误的地方。

这和这个项目要解决的核心问题是同一类。判断 SQL 对不对时，官方那套"两个集合相等就算对"
的判据，同样是一个只看表面就宣布通过的验证器——只不过被它放过去的不是损坏的字节，
而是模型的取巧行为。
