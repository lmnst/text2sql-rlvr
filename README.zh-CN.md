# Text2SQL-RLVR

[English](README.md) | **中文**

如果把数据库本身当老师，一个小的开源模型能不能学会在又大又乱的真实数据库上写出正确的 SQL？
这个项目在 BIRD 数据集上用 Qwen3 系列模型回答这个问题。模型写出的每一条 SQL 都会在只读的
数据库副本上真实执行，执行结果有三种用途：强化学习时的奖励、筛选哪些训练数据值得保留的
标准，以及模型在提交答案前可以主动调用、用来检查自己的工具。

## 项目进展

- **8 月，Qwen3-1.7B：** 从数据处理、SFT 到 GRPO 的完整链路已经搭建并完成评测。
- **9 月起，Qwen3-4B：** 生成模型换到更大的底座，并重新设计了整体方案（见下一节）。这部分工作
  在 [`selector-stage1`](https://github.com/lmnst/text2sql-rlvr/tree/selector-stage1) 分支上
  （[PR #1](https://github.com/lmnst/text2sql-rlvr/pull/1)）。

## 当前方案（Qwen3-4B）

```text
问题 ─▶ 选表 ─▶ SQL 生成模型（Qwen3-4B）─▶ 最终 SQL
                    │            ▲
                    ▼            │
              只读数据库：执行、观察结果、修改
```

**1. 给模型更少、但更准的上下文。** BIRD 的一个库可能有几十张表。生成之前，先用词面匹配、
一个训练过的小选表模型、再沿外键扩展一跳，把 schema 缩小。如果还漏了需要的表，模型可以在
agent 循环里自己查。

**2. 针对模型答错的题训练。** SFT 数据不随机抽取，而是先让基座模型把整个训练集答一遍，
重点微调它答错的题，同时回放一部分已经答对的题，避免已有能力退化。字段选错、聚合粒度不对、
输出格式不对这几类高频错误，额外补充针对性样本。每条训练样本都经过真实执行校验。

**3. 从模型自己的采样里学。** 微调后的模型对每道训练题作答多次，由执行结果分出对错。它自己
最常写出的正确答案和最常犯的错误组成一对偏好数据，用来做 DPO。标准答案只作为有上限的兜底，
因为标准答案的写法和模型自己的风格差别很大，DPO 可能学成模仿风格而不是写对。

**4. 把自我纠错训练成能力。** 在 agent 循环里，模型可以查看表结构、执行查询、读取结果或报错
再修改，最多四轮。最终查询与标准结果一致的完整轨迹会成为训练数据，损失只计算模型自己的回合。
更强的老师模型只在"学生答错、老师答对"的题上使用，而且只有这部分题足够多才值得引入。
否则由学生自举：带着"正确结果应该是什么形状"的提示重做自己的错题，训练时去掉这个提示。

**5. 补上执行器给不了的信号。** 剩下的大部分错误是能正常执行、但返回了错误行的查询。
用两个低成本的信号针对它们：结果里有没有完全重复的行；以及让模型先说出正确答案应该有
哪些行和列，再和查询的实际结果对照。

## Qwen3-4B：目前的结果

以下各行都在固定的 788 题验证集上、使用 linked schema 和贪心解码得到。

| 配置 | official EX | run_id |
|---|---:|---|
| Qwen3-4B 基座 | 34.01% | `a9eaa7f7da3e` |
| 基座 + agent 循环（最多 4 轮，未训练） | 33.50% | `27c6fe6380c4` |
| 基座 + oracle schema（选表的上界） | 41.62% | `02fd984e7873` |
| + SFT，随机 1500 条 | 42.39% | `2c82eb0ead22` |
| + SFT，按基座答错的题选 1500 条 | **45.30%** | `c0c001faa315` |
| + SFT，构造 550 条 + 选题 950 条 | 44.16% | `cc9818e2eeaf` |

- 三组 SFT 都明显优于基座（p < 0.0001）。SFT 是目前最大的单一杠杆，比给基座一份完美的
  schema 提升还大。
- 按模型自己答错的题选数据，比随机选高 2.91 个点（p = 0.0385），提升主要集中在表最多的
  那个数据库上。

## 目前的结果（8 月，Qwen3-1.7B）

每一行都能在 `results/runs.jsonl` 里唯一定位。

| 模型 / 提示 | 划分 | n | BIRD official EX | Strict EX | run_id |
|---|---|---:|---:|---:|---|
| Qwen3-1.7B 基线 | Mini-Dev | 500 | 19.80% | 17.40% | `43bb66bbe1e8` |
| LoRA SFT | Mini-Dev | 500 | 34.60% | 30.00% | `f1ef9b247255` |
| 强 SFT，完整 schema | 固定 train-val | 788 | 32.87% | 28.68% | `74d4d83c087c` |
| 强 SFT，linked schema | 固定 train-val | 788 | 37.94% | 33.63% | `3b9e91f891d8` |
| 官方口径奖励 GRPO，linked schema | 固定 train-val | 788 | 38.20% | 33.88% | `53d1586c7d33` |

只有同一划分内的行可以直接比较：

- linked schema 让强 SFT 模型的官方 EX 从 32.87% 升到 37.94%。
- GRPO 让 linked schema 下的官方 EX 从 37.94% 变为 38.20%，判定为没有明确的额外提升，
  而不是 RL 成功。最可能的原因是 0/1 奖励太稀疏：一道题采样的答案全对或全错时，这一组
  提供不了任何学习信号。
- 788 题是从 BIRD train 里固定划出的验证集，它的三个数据库在训练中完全没有出现。
  BIRD dev 从未被读取，既没用于调参，也没用于任何其他用途。

## 过程中学到的

**上下文少一点有帮助，但有限度。** 把数据库从 42 张表缩到约 25 张，执行准确率大约提高 3 个点。
训练过的选表模型加上外键扩展能把输入压得更小：平均从 25.5 张表降到 7.8 张，同时在 95.7% 的
验证题上保住了所有需要的表，但执行准确率没有超过词面匹配。
和 oracle 之间剩下的差距来自"恰好只给标准答案用到的表"，这等于泄露了表的连接结构，真实的
选表模型做不到。

**执行反馈修得了崩溃，修不了理解错误。** 让模型执行查询后修改，788 题里执行失败从 142 条
降到 55 条，但准确率没动：四分之三的错误是能正常执行却返回错误行的查询，比如该用
`COUNT(DISTINCT ...)` 的地方用了 `COUNT(*)`。上面第 4、5 步正是从这个发现出发的。

## 怎么保证数字可信

- **同一批预测，两套指标。** `official_ex` 复刻 BIRD 官方评分，是奖励和主指标；`strict_ex`
  额外保留重复行并检查列数。更严格的那套发现了 933 条漏掉必要去重、却仍被官方评分算对的答案。
- **模型写的 SQL 在沙箱里运行。** 只读访问、一次只允许一条语句、硬超时、禁止任何写操作。
- **只追加的实验台账。** 每次评测都记录 Git 提交、数据划分、解码参数和输出文件，每个数字都能
  追溯到产生它的那次运行。

## 运行

测试不需要 GPU，会自己创建临时数据库：

```bash
pip install -r requirements-dev.txt
python -m pytest -q
```

数据下载见 [docs/data.md](docs/data.md)。GPU 相关依赖单独固定在 `requirements-train.txt` 中。
SFT 和 DPO 的训练器是基于 transformers 和 peft 的单文件脚本，GRPO 使用 verl。

## 小结

目前最明确的提升来自 schema linking，以及按模型自己的错题挑选微调数据。没有带来提升的实验，
比如稀疏奖励下的普通 GRPO、单靠执行反馈的自我修正，都连同各自的诊断一起记录下来，这些诊断
直接决定了现在的方案。
